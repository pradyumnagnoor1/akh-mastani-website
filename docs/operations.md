# Operations and annual handover

These procedures are not installed automation or completed live validation. Before launch, record the responsible people, alert destination, backup location, recovery evidence, and accepted recovery targets in a private team-owned handover record. Never store passwords or exported dancer/payment data in this repository.

## Ownership and routine work

Initial application admin: **pradyumnagnoor@tamu.edu**, after verified Google onboarding and the bootstrap script. Infrastructure ownership is separate from app admin permission. The owner must designate a backup maintainer and give them appropriate recovery access without automatically granting dancer-management rights.

| Cadence                                | Responsible role and action                                                                                                                                                                            |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Every day during season                | Maintainer checks backup success and unresolved service alerts; admin checks pending membership/payment reports                                                                                        |
| Before each practice                   | Team admin checks calendar sync timestamp and reconciles questionable events with Google Calendar                                                                                                      |
| Monthly                                | Maintainer reviews dependency/security updates, provider quotas/billing, error trends, backup retention, and credential ownership; run checks before release                                           |
| Each semester and after backup changes | Maintainer restores database and Storage into an isolated project and records results                                                                                                                  |
| Annually, before officers leave        | Owner transfers repository, Vercel, Supabase, Google Cloud/calendar, domain, billing, monitor, and backup vault recovery access; incoming maintainer performs a restore drill and deployment rehearsal |

Handover records should include project IDs/URLs, owner and backup contact, renewal dates, deployed commit, migration ledger, last backup and drill times, calendar-authorizing account, secret names/rotation dates, and recovery procedure. Verify incoming accounts work before removing outgoing access. Rotate shared credentials and revoke old access. Delete old segments/posts/groups only when their permanent removal is intended, and deactivate departing members; preserve member UUIDs and private payment history. Migration0009 deletes non-payment audit/assignment records with the source; see management.md. Never repurpose a former member record for a new dancer.

## Monitoring and incident response

Configure an external monitor to request `/api/health` every five minutes and notify the maintainer after two consecutive failures. This endpoint is **liveness only**: success proves a responding application route, not database availability, Google sign-in, Storage access, calendar freshness, or correct authorization. No monitor or alert service is provisioned by this repository.

Review Vercel function errors and Supabase Auth/database/Storage logs after releases and on reported failures. Log only timestamp, route, status, duration, deployment identifier and sanitized failure code; exclude cookies, bearer tokens, OAuth credentials, member emails, payment references and exported contents. Check provider usage dashboards for approaching storage/egress/function quotas. Confirm alert delivery during launch acceptance.

For calendar monitoring, an authorized operator opens Practice Calendar and checks its displayed successful-sync timestamp and stale/error state. The five-minute target applies while used; idle periods alone are not incidents. If a fresh request still fails after the cooldown, inspect sanitized `authorization`, `timeout`, `upstream`, `capacity`, `invalid_response`, or `storage` status as explained in [calendar recovery](calendar-setup.md). Do not make the calendar endpoint public for monitoring or falsify its success timestamp. During a Google outage, the last complete snapshot may remain visible with a stale label; confirm urgent changes in the source calendar. A Supabase outage can prevent even cached reads.

For an incident, record start time and affected feature, assess Vercel/Supabase/Google status, and restore service before broad investigation. Follow [deployment rollback](deployment.md) for release failures. For suspected credential exposure, revoke/rotate the affected credential and inspect access history. After recovery, verify identity/privacy boundaries with two accounts, reconcile uncertain payment or upload actions before retrying, and record cause and corrective work.

## Operational export

An active admin can download JSON from `/api/admin/export` using their signed-in session. It contains members, segments and assignments, posts and recipient progress, saved groups and memberships, live charges and their payment audit history; deleted payments/history remain only in owner database backups. Other audit tables are not included. Treat the file as private team and financial information: save only to approved encrypted storage and remove unneeded local copies.

The export has a 3 MB data budget and a 20,000-row limit per table. An over-limit export must be handled through the database backup process; do not delete history to make it fit. Reads span multiple requests and are **not transactionally consistent**. This is an operational handover snapshot, not a complete recovery backup: it excludes Auth identities, credentials, full provider configuration, and PDF object bytes. It cannot recreate sign-in identities or restore formation files, and there is no application import route. The endpoint uses the admin's session rather than the calendar's privileged key.

## Backups: database and actual Storage bytes

Proposed initial recovery targets are at most 24 hours of lost changes and restoration within one working day; the owner must accept or revise them and prove them in the drill. Configure a daily backup job with failure notifications and an extra recovery point before migrations. Until that automation exists and succeeds, the maintainer must perform and record the procedure manually; a document is not a backup.

1. Use the provider's supported database backup or [Supabase CLI backup/restore procedure](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) to capture schema, roles and data, including the Auth identities needed to preserve member UUID relationships. Verify which managed schemas, role credentials and settings the selected method excludes. Preserve migration versions and provider configuration inventory separately. Use secret-store injection and a restricted temporary directory; do not put a database password in shell history or logs.
2. Export **every actual object byte** from the private `formations` bucket using an owner-controlled Storage/S3 client, preserving object keys, content type, length and a SHA-256 manifest. Include current, historical and retained unreferenced uploads; do not substitute a list of object names or database Storage metadata. Copying all retained objects avoids losing files referenced by audit history. Reconcile the database snapshot and object manifest; a brief coordinated write pause is appropriate for a consistent pre-migration recovery set.
3. Encrypt the database files, Storage files, and manifest before copying them to a separate provider/account/location outside the live project. Keep encryption recovery keys in a team-owned password manager accessible to the owner and designated backup maintainer. Use narrowly scoped backup credentials. Suggested retention: 30 daily recovery sets and 12 monthly sets, subject to the owner's data-retention decision. Restrict access because backups include identity and payment records.
4. Verify upload completion, byte counts and checksums, record UTC snapshot time, source project, application commit, migration versions and backup size, and test decryptability. Alert on missing or failed backup runs. Retain the last known good set until a newer set has been verified.

Supabase database backups contain Storage metadata, **not uploaded object bytes**. Free projects should maintain their own off-site exports; paid backup availability/retention must be checked for the selected plan. See [Supabase backup coverage](https://supabase.com/docs/guides/platform/backups). Free projects can pause after a week of low activity, which matters over summer breaks; see [project pausing](https://supabase.com/docs/guides/platform/free-project-pausing). Neither a Git repository nor the admin JSON export replaces this recovery set.

## Restore drill and disaster recovery

1. Create a separate restricted Supabase project and isolated staging deployment. Never rehearse by overwriting production. Disable production calendar credentials and prevent test users from accessing copied private data.
2. Retrieve an encrypted recovery set from the off-site location with the backup maintainer's access. Verify manifest/checksums and decrypt in a restricted environment. Follow the provider-supported restore procedure for that database format; resolve managed-role/schema behavior before proceeding. Preserve Auth user UUIDs and their member links. Reconfigure OAuth/provider settings using the private inventory; credentials and callback configuration are not restored by application SQL.
3. Restore private Storage buckets/settings and upload the saved PDF bytes at their exact keys. Compare counts, lengths and hashes with the manifest. Confirm active and historical references resolve. A database-only restore is a failed drill.
4. Compare table counts and sampled member/assignment/payment/audit relationships with the backup manifest. Validate RLS and Google identity using controlled admin/dancer accounts; prove cross-member payment/task access fails, deactivated users fail, and private PDFs remain private. Confirm history and outstanding balances agree. Use a dedicated test calendar to verify sync separately.
5. Record elapsed recovery time, recoverable timestamp, verification results, gaps, and operator. Remove temporary decrypted files through the team's secure handling process and retire the restricted drill project when evidence is retained. No drill has yet been performed for this application.

For an actual disaster, preserve the failed system for diagnosis, suspend affected writes, perform the same restore and validation, then update the production deployment to the recovered project URL/keys and exact OAuth callbacks. Expect users to sign in again. Reconcile any changes after the recovery point with the team's payment/source records before resuming writes. Do not automatically replay reports or mark transfers verified.

## Secret rotation

Maintain separate staging/production credentials. For the calendar Supabase secret key, create a dedicated replacement key, update only the server environment, redeploy, verify a fresh authorized sync, then revoke the old key and retire deployments that still use it. This key has project-wide privilege even though this app confines its usage to calendar RPCs. For a leak, revoke first and accept temporary sync failure. Member-facing code must continue to use session/RLS access.

For calendar OAuth failures or officer turnover, have the calendar owner repeat the consent flow in [calendar setup](calendar-setup.md), use Admin → Connect Google Calendar to store the encrypted replacement token, deploy any changed client credentials and verify freshness, then revoke superseded access. Rotate Google sign-in provider credentials in Supabase and Google together and verify the real callback. Database/backup credentials and encryption keys need their own coordinated rotation; keep older encryption keys recoverable until retained backups are re-encrypted or expire. Never revoke the sole recovery key before proving restoration.

Calendar connection credentials are encrypted in the database. Keep `CALENDAR_TOKEN_ENCRYPTION_KEY` separately recoverable in the team password manager; backup/restore requires that key or a fresh admin reconnection. See calendar setup for encryption-key rotation and callback query-log redaction.
