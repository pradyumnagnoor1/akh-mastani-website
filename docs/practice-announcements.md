# Exec roles and practice announcements

The exact role labels are Captain, Logistics & Finance, Production, Social, AO and Hospitality. All six roles give identical full application management access, in addition to dancer participation. Members can hold several roles. Only active members who already have manually granted admin access can receive exec roles; an exec role alone does not make a member eligible for another assignment. Only an existing manually assigned admin can assign/remove roles, under Admin → Members & requests. Eligible members without a role show the selector. After saving, it collapses into **Change exec role**; reopening restores saved roles, and Cancel discards unsaved choices. Controls stay disabled during saving. This does not add an admin-grant control or separate exec pages. Role changes are checked by the database on subsequent operations; inactive members lose access.

Announcements show the original posting name, selected exec role and Chicago posting timestamp. Authors with several roles select which assigned role to publish under. Published attribution stays fixed when names or roles change. Edits have a separate timestamp. Existing posts use available author records; historical exec affiliations are not invented. Unread badges are red, read badges green; acknowledgement remains per recipient.

Choose Announcement or Practice announcement in the composer. Practice announcements select an upcoming timed Google Calendar occurrence or an existing custom practice. Choose **Custom practice (not on Google Calendar)** to enter a practice name, date, Texas start/end times and location while composing the announcement. The event and announcement save in one transaction; a failed announcement leaves no orphan event. Custom practices appear in the same day calendar and can be reused by later announcements. Exec members can edit or delete them from their calendar card, with version checks protecting concurrent changes. They do not create Google Calendar events. The same post and its recipient permissions appear in Announcements and under that practice on Calendar. Recurring links use series + original occurrence start, so a moved occurrence retains its notes; calendar connection fingerprints prevent unrelated replacement calendars from inheriting notes. New links require a current-source snapshot refreshed within 15 minutes. Retained links can still be edited if the practice is absent; its last known details and an unavailable-schedule message remain visible. Google Calendar remains the schedule source for Google events; website-only practices use their own canonical records. Deleting a custom practice removes its audit, retained schedule snapshot and notification details while keeping active announcement messages with an unavailable-practice notice. Shared reminder bundles retain their unrelated tasks/payments.

Calendar defaults to Today in America/Chicago. Day/Upcoming buttons, a date picker, previous/next day and Today controls help navigation. Day shows every matching Google/custom-practice/featured event, including ended, all-day and overnight events; no ten-event cap applies. Featured events with only a start time show Started rather than claiming an unknown end time. Empty days provide the next upcoming event. Cached schedule freshness remains visibly labelled.

## Reminders and previews

A linked announcement has no separate author reminder schedule. It contributes to the existing practice reminder, normally around one hour before start. All linked messages eligible for a given recipient are combined into that recipient’s preview; acknowledgements do not suppress practice preparation instructions. Deletion/expiry removes notes from pending previews, edits rebuild previews at delivery, and source/freshness/event-start checks invalidate cancelled or moved pending reminder jobs. Repeated scheduler calls retain existing occurrence/device deduplication. General announcement reminders keep their author-selected schedule and stop conditions.

Practice reminders show time/location and the recipient’s linked message excerpts. Announcement change alerts show the title, author and message; linked change alerts prefix the title with Practice. No notification preview contains an exec role badge. Practice notification taps open its calendar date. Bundles containing other reminders can link to Today. During the practice reminder window, a publication merges only when a valid pending shared delivery exists for that device. A new note posted after a reminder already sent still gets a publication alert.

Existing opt-in devices, quiet hours (10 PM–9 AM Chicago), smart nudge daily limits, bounded retry, freshness checks and scheduler cadence remain applicable. Publishing a practice announcement after its reminder window does not replay an earlier practice reminder. Push provider receipt, exact timing and physical-phone display require live verification; database/browser fixtures do not establish real delivery.

## Visual hierarchy

Shared page titles use a larger, heavier Hanken heading and violet underline. Section/card titles, row titles, important values, event times and locations have consistent size, weight and contrast, while metadata keeps the muted treatment. The existing dark/violet theme and responsive layouts remain.

## Exec identity on published actions

Announcement and to-do authors show their name, posting/creation timestamp and a violet **Exec role** badge with the saved role. The same badge distinguishes exec identity from audience/status tags on Home, Today, Calendar, Roster and Admin. Both composers offer **Posting as** for assigned roles; edits preserve original attribution even after the author's current roles change. Historical records with no saved role do not invent one from today's membership. Notification previews continue to omit exec role tags.

## Current-month Upcoming and linked to-dos

Calendar **Upcoming** shows remaining events overlapping the current month in America/Chicago, with a month/year heading. Day/date navigation still reaches other months; the Google sync window stays unchanged.

When creating or editing an announcement without a linked task, enable **Also create a to-do** and choose an optional due date and individual/shared completion. Publishing saves both items together. The to-do starts with the announcement title/details and exact captured recipients; it appears in To-Dos with a link back, and the announcement links to that task. Reading and task completion are separate. Later task edits are independent; deleting either keeps the other, and deleting the task removes its announcement link. The task remains actionable if the announcement expires.

The initial paired publication sends one announcement alert per device; attaching a task to an unchanged existing announcement keeps the task alert when no new announcement alert is queued. Normal due-task reminders remain; practice announcements still share the existing practice reminder. Notification previews keep the existing title/message style without exec tags.

Apply `0018_announcement_todos.sql` after0017 before this frontend release. This is additive and preserves existing save entrypoints. No live announcement/task or notification is needed for schema rollout.
